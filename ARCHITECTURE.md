# Architecture

## Overview

LMPdf is a web application for filling PDF forms. A scanned or born-digital PDF is uploaded, field zones are detected or defined manually, and users fill the form fields online. The filled PDF is then exported.

**Approach:** scanned/born-digital PDF as background + positioned field overlays on top. Guarantees visual fidelity without requiring a full CSS conversion of the document.

## Stack

| Layer | Technology | Location |
|---|---|---|
| Frontend | React + Vite + TypeScript | `apps/web/` |
| Backend API | NestJS + Prisma + PostgreSQL | `apps/api/` |
| Vision service | Python (FastAPI / OpenCV / Tesseract) | `apps/vision/` |
| Uploaded files | Local `uploads/` directory, shared Docker volume | `apps/api/src/upload/`, Compose files at repository root |
| Configured services | Garage (S3-compatible), Redis | `docker-compose.yml`, `docker-compose.prod.yml`, `infra/` |
| Runtime | Docker Compose | Repository root |

Garage and Redis are defined as services. The current API upload and export
paths do not use Garage as binary storage, and no Redis client appears in the
current application sources. Do not infer an active S3 or job-queue data flow
from the Compose services alone.

## Frontend (`apps/web/`)

Single-page React application. Renders PDF pages with `react-pdf` / `pdfjs-dist`
and positions field components over them. `exportPdf.ts` generates a filled PDF
in the browser with `pdf-lib` for download or optional server-side export.

**Key components:**
- `App.tsx` — root component, state management, keyboard shortcuts
- `PdfViewer.tsx` — canvas rendering, page navigation, zoom
- `FieldOverlay.tsx` — renders a single field (text, checkbox, counter, date)
- `RichTextEditor.tsx` — `contentEditable` wrapper for inline text formatting
- `SelectionToolbar.tsx` — floating B/I/U/S + color toolbar for text selections
- `PropertiesPanel.tsx` — right sidebar: field properties, font, colors, alignment
- `AutosaveIndicator.tsx` — "Brouillon enregistré" status display

**State:** React `useState` + `useReducer`-style patterns in `App.tsx`. No external state library.

## Backend API (`apps/api/`)

NestJS REST API. All endpoints are under `/api/`.

**Modules:**
- `auth/` — login, register, JWT, MFA (TOTP + WebAuthn), LDAP
- `templates/` — CRUD for PDF form templates (name, fields, PDF file reference)
- `upload/` — handles PDF/image upload and serves files from local `uploads/`
- `drafts/` — draft state persistence between autosave cycles
- `permissions/` — sharing (owner/editor/filler roles per document)
- `detect/` — triggers the vision service for automatic field detection
- `export/` — optional server-side write of a PDF generated by the frontend,
  to an allowed filesystem destination; records export logs
- `folders.controller.ts` — folder hierarchy for organizing templates
- `groups/` — user groups for sharing
- `users/` — user management
- `admin-settings.controller.ts` — instance-wide settings

**Auth:** JWT bearer tokens. Role matrix (`config/permission-matrix.ts`) defines what each role (`owner`, `editor`, `filler`) can do.

**Storage:** Prisma ORM uses PostgreSQL for metadata. Multer writes uploaded
PDFs/images to the API's local `uploads/` directory. In Docker, `uploads-data`
mounts that directory in the API container and `/uploads` in the vision
container. Browser exports are generated client-side; the optional server
export writes to a configured filesystem path. Garage is configured but not
used for these file operations.

## Vision Service (`apps/vision/`)

Python service. Receives a document path and MIME type from the backend, reads
the file from the shared upload volume, and returns suggested field rectangles.

**Detector:** OpenCV line and contour analysis identifies candidate zones;
Tesseract is used for text recognition in the detection pipeline. PDFs are
rendered to images before analysis.

**Communication:** Backend calls the vision service directly (HTTP).

## Infrastructure

```
docker-compose.yml             ← development services
docker-compose.prod.yml        ← standalone production services
infra/
├── garage.toml                ← Garage configuration
├── garage-init.sh             ← Garage initialization helper
├── postgres-data/            ← development PostgreSQL bind mount (runtime)
├── garage-data/              ← Garage data bind mount (runtime)
├── garage-meta/              ← Garage metadata bind mount (runtime)
└── minio-data/               ← historical runtime data, partly Git-tracked
```

**Containers:**
- `lmpdf-backend` — NestJS backend
- `lmpdf-frontend` — Vite development server or nginx in production
- `lmpdf-vision` — Python vision service
- `lmpdf-postgres` — PostgreSQL
- `lmpdf-redis` — Redis service configured in Compose
- `lmpdf-garage` — Garage S3-compatible service configured in Compose

The production Compose file publishes the frontend on port 8080 and keeps the
API and vision service internal. The development Compose file publishes the
frontend and API; vision remains internal.

## Data Flow

```
User uploads PDF
       ↓
  apps/api (upload/) → local uploads-data volume
       ↓
  Document metadata in PostgreSQL
       ↓
  Template created
       ↓
  Vision service reads the same volume (optional detection)
       ↓
  Fields stored in PostgreSQL (per template)
       ↓
  User fills fields in apps/web
       ↓
  Autosave → apps/api (drafts/) → PostgreSQL
       ↓
  Export → apps/web creates filled PDF → browser download
         or optional apps/api (export/) → configured filesystem destination
```

## Security Model

Roles per document:
- **owner** — full access, can delete/sharing
- **editor** — can fill and modify structure
- **filler** — can only fill field values, cannot move/resize/lock fields

The permission matrix (`apps/api/src/config/permission-matrix.ts`) is used by
relevant API operations. Document access checks also exist in their respective
controllers and services.
